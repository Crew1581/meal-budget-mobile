# Архитектура

Flutter/Dart, Android/iOS. Стандартные StatefulWidget, ChangeNotifier,
ListenableBuilder; без DI/state-management framework и пустых слоёв.

## Структура

- `lib/main.dart`: однократное создание ресурсов, конфигурация и запуск.
- `lib/app.dart`: оболочка Material 3, вкладки, lifecycle, подтверждения.
- `features/questionnaire/`: валидация/сериализация и сохраняемая форма.
- `features/connection/`: установка, single-flight регистрации, secure storage.
- `features/generation/`: неизменяемая Operation и контроллер отправки/polling.
- `features/menus/`: разбор серверного результата и offline-представление.
- `core/api_client.dart`: package:http, Bearer, безопасные ошибки, Retry-After,
  запрет redirect/retry, abortable HTTP с 20-секундным deadline.
- `core/local_store.dart`: sqflite, транзакции и схема v1.
- `core/server_config.dart`: URL, изоляция хранилищ, debug HTTP/release HTTPS.

## Хранилища

OS secure storage хранит installation_id + Bearer одним JSON-значением; ключ
включает нормализованный URL backend (scheme/host/port/base path). Регистрация
не считается завершённой до успешной записи и контрольного чтения. Ошибка чтения
не трактуется как отсутствие токена. iOS использует `unlocked_this_device`.
Android: `resetOnError: false` явно задан в конструкторе и во всех операциях
`SecureCredentials` (с сохранением прочих настроек внедрённого storage).
Native-ошибка расшифровки превращается в безопасный `ConnectionFailure`, не null.
Удаление ранее подтверждённых credentials — только reset после подтверждения
пользователем; очистка собственной неопубликованной записи при отмене описана ниже.

`CredentialStore.coordinationNamespace` задаёт стабильную идентичность backing
storage, общую для разных обёрток, а не `this`/ID владельца. SecureCredentials
использует effective Android data-prefs namespace либо iOS service/access group.
Внутри одного isolate общий coordinator индексируется парой **namespace + ключ
нормализованного backend URL**. Другой адрес не делит его очередь и ревизии.
Coordinator не кэширует ID/Bearer; existing() читает secure storage в общей очереди,
поэтому после reset/смены владельца нет устаревшего `_known` отдельного сервиса.

Порядок регистрации и сброса:

1. ensure одного сервиса — single-flight. Новая попытка другого сервиса получает
   общую ревизию и вытесняет предыдущую незавершённую попытку для той же пары.
   Уже сохранённая установка переиспользуется, не регистрируется повторно.
2. Чтение credentials упорядочено. Если записи нет, HTTP-регистрация выполняется
   **вне** очереди: старый транспорт, игнорирующий abort, не держит нового владельца.
3. До write в общей очереди проверяются ревизия и отзыв попытки. В секции остаются
   write, контрольное чтение и проверка после каждого await до публикации результата.
   Поздний 201 отозванной попытки не начинает запись, даже если HTTP проигнорировал abort.
4. dispose контроллера синхронно отзывает регистрацию сервиса, затем посылает abort.
   Если write уже начался, его Future и очистка **собственной неопубликованной**
   записи завершаются в той же секции до любого чтения/записи нового владельца.
   Завершённые ранее credentials при dispose не удаляются. Ошибка storage не
   запускает автоматический reset: доступ всех сервисов пары блокируется до
   успешного явного сброса, включая ошибку очистки неопубликованной записи.
5. Подтверждённый reset сразу меняет общую ревизию, затем в очереди удаляет credentials
   и очищает прежнюю SQLite-операцию. Новый владелец допускается к credentials только
   после обеих стадий: старое продолжение reset не может удалить его новую операцию.
   Очередь не ломается после ошибки; неудачный reset остаётся fail-closed.

Reset разрешён и во время регистрации/сохранения токена. Отдельная connection-epoch
контроллера не даёт прежнему create после reset отправить генерацию или изменить
busy/сообщение новой попытки. Старый finally сервиса также не очищает новый single-flight.

**Граница гарантии:** это порядок в одном isolate приложения для вызовов через
InstallationService, не platform CAS и не межпроцессная блокировка. Все обёртки
одного backing storage обязаны сообщать одинаковый namespace. Уже начавшийся
неотменяемый write может временно физически записать старое значение, но новый
владелец/успешный reset ждут его завершения и очистки. Очередь не освобождается
по таймауту зависшего storage: безопасность приоритетнее допуска новой генерации.
Контракт предполагает, что Future storage обозначает завершение упорядоченного
эффекта. Нет обещания rollback/fsync при OS-crash, прямых записях в обход сервиса
или из других isolate/process. До успешного завершения reset его удаление не
гарантировано. Secure storage и SQLite не становятся общей атомарной транзакцией.
Отмена HTTP также не отзывает уже созданную на backend установку/регистрационную квоту.

SQLite `meal_budget.db`, `user_version=1`:

- `draft`: единственная редактируемая анкета, включая незавершённый ввод;
- `operations`: одна текущая операция на URL сервера, ключ/JSON-снимок/установка,
  время первой отправки/deadline, job_id, phase/error_code и Retry-After deadline;
- `menus`: ключ `(server, id операции)`, дата, JSON результата без metadata.

Схема создаётся `onCreate`; для следующей версии потребуется явная миграция
в onUpgrade. Fallback с удалением БД отсутствует. Данные SQLite не шифруются,
токен туда не попадает. Secure storage и SQLite — не общая транзакция: сначала
долговечный токен, потом операция, потом HTTP. completed и меню фиксируются
одной SQLite-транзакцией. Названия ингредиентов берутся из сохранённого
shopping_list, не из актуального публичного каталога.

## Протокол и жизненный цикл

Корневой `HomeScreen` владеет контроллером, который создаётся в main и передаётся
через `MealBudgetApp`. Экран снимает observer и вызывает dispose при окончательном
удалении. При замене инъекции прежний контроллер освобождается, при обычном rebuild
и навигации с тем же экземпляром — нет. Callers не вызывают повторный dispose.
До передачи владения ошибка bootstrap освобождает созданный контроллер в main.
Unit-тесты без UI владеют контроллером самостоятельно.
Каждый контроллер владеет своим InstallationService и отзывает его при dispose;
уничтоженный сервис не передаётся следующему контроллеру. Новый сервис использует
тот же общий coordinator и сохранённую установку, а не начинает регистрацию заново.

`create`: single-flight → ensure installation → атомарная запись операции → POST.
Повторное нажатие/редактирование не меняет ключ и снимок. 202 сначала фиксирует
job_id. Если запись job_id не удалась, ID остаётся в памяти и может быть сохранён
при ручном GET; после crash остаётся прежний снимок для явного восстановления.

При старте job_id продолжает только GET, неизвестный POST ждёт пользователя.
Восстановление требует прежнюю установку и подтверждённый deployment deadline.
Backend TTL не обнаруживается автоматически. Известный job_id никогда не
заменяется новым POST из-за ошибки GET. HTTP 404 завершает локальное ожидание
как `missing`, не подменяет server state `failed`.

Polling: последовательный GET, 2 секунды после ответа, transient backoff
4/8/16/30 секунд, Retry-After имеет приоритет. Background отменяет таймер и
передаёт abort текущему GET; resume возобновляет ожидание без нового POST.
dispose отменяет таймер, GET и lifetime-abort для POST/регистрации. Проверки после
await не дают позднему ответу начинать сохранение результата, следующий GET или
уведомление уничтоженного UI. Уже начатая SQLite-транзакция может завершиться:
это не rollback и не отмена серверной генерации. Terminal останавливает polling. 401/прочие
нетранзиентные ошибки останавливают автоматические GET до явной проверки.
worker_unavailable остаётся нетерминальной ошибкой доступности.
Защита регистрации находится не только в этих проверках контроллера: coordinator
сервиса ограждает сам побочный эффект в secure storage, в том числе запись в процессе.

Ошибка сети/503/неразобранный ответ POST сохраняют неизвестный исход.
Нового автоматического платного задания нет. Токены, формы, меню и сырые
исключения не логируются приложением. Плагин 10.3.4 самостоятельно пишет native-
диагностику в logcat; опции её отключения нет, сырой вывод не копируется в отчёты
native-runner. HTTPS не отключает проверку сертификатов.
